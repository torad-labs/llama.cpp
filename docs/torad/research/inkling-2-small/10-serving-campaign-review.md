# Inkling 2 Small on four RTX PRO 6000s

The subsequent rental used four 96 GB RTX PRO 6000 Blackwell Server Edition cards. [Physical measurements and serving results](12-four-card-serving.md)

The five optimization items identify worthwhile kernels. They miss the pauses people see during a long prefill and the cost of rereading a session after its slot has been reused. The campaign's Q4_K crossover on an unsplit matrix also measures a different operation from a rank's share of the abliterated Q3_K_M model. Keep the fused relative attention, its dense reference and the independent KV precision controls. Judge the service on a mixed workload with the actual pack.

## The work configuration

Issue #255 records the GLM deployment on four 97,887 MiB RTX PRO 6000 Blackwell Server Edition cards. The cards were connected through two PCIe switches. A single 200k-token prefill lowered the measured peer stream from 47.6 to 11.7 tokens/s for 50 seconds, alongside four to five occupied user slots. This is the production comparison for prompt scheduling. [Reported load and measurements](https://github.com/torad-labs/llama.cpp/issues/255)

| Setting | GLM work deployment | Inkling Q3_K_M starting profile |
|---|---|---|
| GPUs and sessions | Four equal tensor ranks, 23 slots, unified KV | Same |
| Total pool / maximum per session | 3,014,656 / 262,144 tokens | 2,359,296 / 294,912 tokens |
| Prompt handling | 2,048 logical and physical batch, 1,024 prompt step, 128 chunk | Same, with independent microbatch and prompt controls |
| Inactive sessions | 256 GiB RAM cache with async save and restore in the long-context report | 32 GiB by default, configurable with `--cache-ram` in MiB |
| Precision | IQ3_XXS weights, Q4 latent KV and Q8 indexer | Abliterated Q3_K_M with imatrix, F16 KV |

The earlier GLM run used a 32 GiB cache and synchronous transfers. Its follow-up changed both the cache budget and the copy mode together, so the recorded speed difference cannot establish the contribution of either change alone. [GLM cache experiments](https://github.com/torad-labs/llama.cpp/issues/238)

The 23 slots draw from one pool according to use. Each Q3 session shares its 294,912-token window between its complete prompt and generation. As in the GLM launcher, the server default for maximum generated tokens is unlimited within the available context. A client can request a shorter completion. Eight sessions at the 294,912-token limit consume the nominal pool. Raising that pool to GLM's reported size costs another 20 GiB of global F16 KV across the four GPUs (5 GiB per rank for an even split). This excludes sliding-window state, graph buffers and allocation overhead. Measure the least-free card after loading the actual pack before increasing the pool. With the same Q3 GGUF at the GLM pool size, Q8_0 global KV is an estimated 48.875 GiB, compared with 92 GiB for F16. The launcher accepts `--kv-cache q8_0 --swa-kv-cache f16` to measure that option while retaining sliding-window precision.

The fork's converter read the actual configuration, tokenizer and tensor headers from all 24 pinned safetensors shards. The data regions were sparse placeholders for this sizing run. The fork's Q3_K_M quantizer dry-run on the resulting 1,092 text tensor descriptors projected **264.05 GiB** of text weights (3.82 bits per weight). It selected Q3_K for all 48 merged gate/up tensors, Q5_K for the first three down tensors and Q4_K for the other 45. Routed experts account for 260.56 GiB of the total. No weight payload or calibration examples were processed in this dry-run.

|---|---:|---:|---:|
| 2,359,296 tokens, F16 | 72.00 GiB | 336.05 GiB | 11.58 GiB |

The space left must cover the sliding-window KV, recurrent state, compute and graph allocations, CUDA runtime, projector and any imbalance between ranks. The quantizer also projects about 1.08 TiB for an F16 text intermediate. A conversion using that intermediate and retaining the source and output together needs roughly 1.70 TiB before temporary files, calibration data and the projector. The intermediate and the final pack have different storage requirements.

## Reasoning effort for coding clients

Inkling takes reasoning effort as a value in a system message. The pinned template maps `none` to 0, `minimal` to 0.1, `low` to 0.2, `medium` to 0.7, `high` to 0.9 and both `xhigh` and `max` to 0.99. The default is `high`. Each value uses the same conversation window. Selecting a named level sets no output-token or thinking-token budget.

| Client endpoint | Fields to add to the request for high effort |
|---|---|
| `/v1/chat/completions` | `{"reasoning_effort":"high"}` |
| `/v1/responses` | `{"reasoning":{"effort":"high"}}` |
| `/v1/messages` | `{"output_config":{"effort":"high"}}` |

Web chat's Off switch, a server started with `--reasoning off`, and the Messages API's `{"thinking":{"type":"disabled"}}` now render native effort 0. The normal profile leaves the choice to each request. The 3-bit fixture received the expected tokenized prompt for all seven level names on all three endpoints. With the derivative's actual tokenizer, the seven rendered prompts matched the pinned Hugging Face template byte for byte and produced six distinct token sequences. The two names for 0.99 share one sequence. A separate request omitted its output limit and remained active until the test client disconnected after receiving 33,000 tokens. The full pack still needs behavioral evaluation on coding tasks at each effort.

## Changes specific to this workload

- The Q3_K_M expert projection is normally Q3_K for merged gate/up and Q4_K or Q5_K for down. The splitter assigns 512 intermediate channels to three ranks and 768 to the fourth, rotating by layer. The six 23-row local benchmarks cover those widths, including both halves of gate/up. The former campaign crossover at 12 full-width Q4_K rows no longer changes the default for other GPUs and models. The SM120 experiment compares the grouped kernel with the row kernel at the same 23 rows. A single-card operator timing excludes the collective.
- Relative attention retains one position per KV cell and computes the distance inside attention. Its host input now uses the existing contiguous position vector. The launcher uses the packed mask on supported fused paths by default. Use `--no-attn-mask-bits` for the dense comparison. Probes and legacy bias addition receive a dense mask. At the proposed pool size, a full-width global mask with 2,048 query rows occupies 9 GiB dense or 576 MiB packed. At 23 query rows the figures are 103.5 MiB and 6.47 MiB. These sizes apply to that tensor at full extent.
- Layer fusion is partly realized. The graph combines residual mixing, each norm clip, and sigmoid times attention into dedicated operations. In the graph, the clip follows a separate projection. The convolution also still joins history with the input and stores a state row separately. Node coverage and state comparisons establish correctness for those paths. A device trace is needed to establish the share of decode time that kernel launches still consume.
- Short convolution uses independent prompt positions to parallelize prefill. The graph joins only the state tail needed by the next step or a rollback. For 2,048 tokens, four taps and ordinary decoding, the three concatenation outputs per layer total 0.30 MiB instead of 156.23 MiB across ranks. The sharded hidden convolution can append its strided input directly to history, eliminating two local layout copies per layer on the fused path. Inter-rank gathers and expert reductions remain part of the workload.
- On an exact extension of a complete cached prefix, both RAM lookup and prompt preparation now continue from the saved recurrent state. Previously both paths interpreted the last recurrent position as the start of a sliding window and lost all reusable tokens. The server leaves idle sessions on device until a slot is reassigned or KV space is needed. Ordinary slot exchanges can save and restore in the background. Under KV pressure, the server tries to save the oldest idle slot synchronously. A snapshot that cannot fit may require a later prefill. The Inkling launcher exposes the host cache size, checkpoint count and synchronous or asynchronous transfers.

## A bounded first run on the four cards

Start with the pinned abliterated source and inspect the produced GGUF tensor types, hash, shards and projector before measuring. The full derivative text GGUF still needs conversion and calibration. The pinned F16 vision projector was converted locally from all 422 visual tensors, fetched as one contiguous byte range of the final source shard. The rebuilt CUDA vision engine encoded an 80 x 80 test image with these weights and produced four 4,608-dimensional image embeddings with finite values and a nonzero combined norm. Its SHA-256 is `06e2b478ca029ab3aea9ed041032079401e168274c248d6eba39081c375ff031`. [Pinned source revision](https://huggingface.co/benthecarman/Inkling-2-Small-abliterated/tree/e4853745aa9cb4587e8959d3c80b92e1bef99a4a)

The derivative author has since uploaded a second pass that changes all 24 model shard hashes. The launcher retains the campaign's first revision. The header-only conversion of the second revision produced the same 1,092 text tensor names, shapes, types and projected size. The second-pass model card attributes most reported benchmarks to the first version. Both derivative revisions set `log_scaling_n_floor` to 128,000. The stock release changed this to 8,192 on November 17. This parameter controls when the global layers start increasing their query and relative-position scales. The converted header from the pinned source contained 128,000. Compare the derivative at its own setting first and include long-prompt checks across that threshold. [Second derivative revision](https://huggingface.co/benthecarman/Inkling-2-Small-abliterated/tree/8574652a49e1f39286b25cb943e57e08ec931b17) [Stock configuration change](https://huggingface.co/thinkingmachines/Inkling-2-Small/commit/1df2d97d45210d94f781f42a6521392e5a539e46)

1. Use the Q3_K_M pack with F16 KV and measure the least-free card after model load, graph warmup and deep requests. Keep the 294,912-token coding slot when varying the overall pool.
2. Measure solo decode and 23-way decode. Run a cold 262,144-token input alongside 22 streaming sessions and request 512 output tokens. The mixed driver reports the reader's time to first token and each peer's p95 and maximum delivery gaps, before and overlapping the reader. It requires each peer to span the reader. Compare scheduling and packed-mask settings on the same weights, prompt IDs and context sizes.
3. Exercise slot reuse at mixed depths and compare the next logits after RAM restoration with fresh prefill. Compare F16 and Q8_0 KV on the same long conversations. For coding quality, give the real pack a repository change with relevant source early and late in a tokenized prompt of at least 262,144 tokens. Apply the generated patch in an isolated checkout and run the repository tests.
4. Profile one four-rank trace at the slowest observed case. Separate attention, expert GEMMs and collectives, short convolution and scheduling. Choose the reduction transport using this host's PCIe topology.

From the worktree, these commands print the four-device plan and run the mixed workload against an already-running server.

```sh
python3 scripts/inkling2/serve.py --profile tensor-4 --server "$PWD/build-campaign/bin/llama-server" --cache-ram 262144 --attn-mask-bits --keep-graphs 32 --dry-run
python3 scripts/inkling2/mixed_prefill.py --url http://127.0.0.1:8103 --sessions 23 --reader-tokens 262144 --reader-output-tokens 512 --check-restore
```

The workload client can request `--reader-output-tokens 32768` after a 262,144-token prompt to fill the window exactly. The mixed driver sends synthetic token IDs and stops peers after they deliver a chunk following the reader's first token. It reports client delivery gaps, which can span multiple tokens if the server coalesces a UTF-8 sequence. The reader window includes request admission, prefill and delivery of the first token. It checks the final server timing for the exact input and output lengths, zero cached input tokens and no truncation. After streaming ends, `--check-restore` takes over a slot, resumes the displaced prompt in another slot, and compares the greedy ID and top 32 log probabilities with both resident and cold controls. It reports the count of overlapping top tokens and checks the exact cached lengths. The existing `scripts/glm53/isolation.py` driver separately exercises shared system prompts, disconnections and slot takeovers.

## Local validation

The HTTP workload ran on a three-layer CPU fixture at 3 and 23 clients. With a separate Q3_K_M fixture, the rebuilt CPU server returned all 128 token log probabilities at each of three prompt depths and 22 streaming peers spanned a 160-token cold reader. The synthetic Q3 fixture uses 512 hidden and 1,024 intermediate channels, two experts, a Q3_K merged projection and Q4_K down projections with one layer explicitly set to Q5_K. It tests mixed types through the real loader and server. Its timing and accuracy do not predict those of the abliterated checkpoint.

All seven existing Inkling converter tests, all 18 launcher tests and three server HTTP cache tests passed. The server regression first reproduced zero reusable tokens after a 100-token prompt was saved. With the correction, the compact sliding-window server restored 100/100 into a different slot. All 128 next-token log probabilities equaled cold prefill on CPU. The rebuilt server also passed the same exchange on the mixed Q3 fixture. On the 5070 Ti, the Q3 server also served 23 clients with one CUDA rank and with four logical tensor ranks mapped to the same device. All 22 peers spanned the cold reader in each layout. At three prompt lengths, the single-rank GPU, four logical ranks and CPU each chose the same next token. Four logical ranks exercise tensor splitting and the server state path on one device; bandwidth and memory per physical rank require the target host.

Both GPU runs restored all 100 cached tokens. Synchronous and asynchronous copies produced identical values across all 128 next-token log probabilities in each layout. Against cold prefill, the maximum absolute difference was 0.00472 on one rank and 0.00401 on four logical ranks. Both exceeded the exploratory 0.002 threshold. A continuation kept on-device also differed from cold prefill, by 0.00607 and 0.00454 respectively. All variants selected the same next token. This controls for the transfer mode and records the size of normal path variation on this fixture.

A 256 GiB RAM-cache dry run selected 23 slots, four equal tensor ranks, async state transfer, 32 retained graphs and the 262,144 per-session cap. At the time of this first pass, the hybrid sliding-window cache could retain graphs only for the same sequence IDs.

On one RTX 5070 Ti, 48 selected registered engine checks passed. They cover packed-mask decode, churn and independent streams on CPU and CUDA, along with tensor-split outputs and state on two ranks on one card. They also exercise convolution, KV precision and 18 CPU-reference routed expert cases at 17, 23 and 32 rows. The full-width unsplit MoE operator sweeps were outside this selection. A separate CUDA event comparison of the serial and token-parallel convolution passed at all 11 shapes, with identical output at every element. At 2,048 tokens, dynamic K/V convolution on a 256-channel shard went from 967.20 to 13.26 microseconds. Static hidden convolution on a 1,152-channel shard went from 515.37 to 30.36 microseconds. At 23 one-token streams, the two implementations took about 1.6 microseconds each.

A second comparison used shared memory to read consecutive prompt tokens and write consecutive channels. At 2,048 tokens on the same card, this reduced the dynamic 256-channel case from 11.60 to 8.00 microseconds and the static 1,152-channel case from 29.53 to 16.89 microseconds. The output matched at every element across 28 shapes, including strided multi-sequence inputs and a prompt longer than 65,535 tiles. The comparisons used separate runs, so compare times within each run. Four-tap SM120 prefills now use the tiled kernel at 512 tokens, or at 128 tokens for static convolutions with at least 1,024 channels. Shorter requests keep the earlier dispatch. ## Second local review

The final residual mix originally processed every prompt row before selecting the requested logits. For a sparse prefill of at least 256 rows, the fused graph now selects the requested rows from the depth sources first. Dense requests, short batches, pipeline-parallel graphs and multi-device data-parallel graphs keep the late selection. A microbatch that only advances session state skips the output head. RMS normalization runs only on output rows. The per-layer Q, K and V input norms now read their row views directly, including the three distinct views in global attention.

On a 5070 Ti, using the same pre-review residual kernel in both graphs isolated the cost of moving this work. At 2,048 prompt rows and one output, the nine-source output mix plus normalization and row selection took 1,083 us before selection moved and 34 us after. At 23 requested outputs it went from 1,072 to 40 us. At 128 prompt rows with one output, early selection was slightly slower (32 vs 31 us). For a 2,048-row global-attention input, the three views with their learned RMS norms took 654 us with materialized copies and 299 us with direct reads. All selected outputs matched elementwise. With the updated depth-mix kernel, the same 2,048-row comparison measured 676 to 17 us for one output and 655 to 25 us for 23 outputs. These are graph fragments at the production hidden width of 4,608. [Paired graph measurements](data/rtx5070ti-output-rows.csv)

SM120 now keeps a depth source in registers through the softmax-weighted sum. At 23 decode rows and nine sources, one query took 5.95 us (previously 23.01 us), and three took 8.17 us (previously 30.06 us). The larger prefill with only one or two sources retains its earlier dispatch. All 90 combinations were compared with the original CUDA result, with a double-precision reference on the first, middle and last token. The five CUDA-versus-CPU backend cases passed Compute Sanitizer memcheck. [Paired depth-mix measurements](data/rtx5070ti-depth-mix.csv)

The L2 clip keeps the model's 16- and 128-channel rows in registers, and two 16-channel rows share a warp. On 2,048 tokens and 12 heads per rank, the 16-channel relative clip took 4.12 us (previously 16.94 us) and the 128-channel Q clip took 19.37 us (previously 20.79 us). At 23 tokens these took 1.28 and 1.80 us. All 15 cases matched the original kernel at every element, including strided inputs and a different head width. [Paired clip measurements](data/rtx5070ti-clip.csv)

On a Ryzen 7 9800X3D, constructing 23 packed global mask rows over a 2,359,296-cell pool took 96 to 113 us using the membership bitmap, down from 6.30 to 6.33 ms. All eight mask pairs had identical hashes. On the 5070 Ti, when each of 23 sequences owned at most one eighth of the indexed KV span, the dedicated relative decode kernel visited only visible keys. At 262,144 cells and 12 query heads per rank, attention took 1.13 to 1.49 ms with F16 KV, compared with 5.19 to 5.39 ms using MMA. The Q8_0 cases took 1.19 to 1.37 ms. The largest absolute output difference from MMA across the 12 synthetic cases was 0.000161. Denser rows keep the existing dispatch. [Mask construction](data/ryzen9800x3d-packed-masks.csv) [Packed decode measurements](data/rtx5070ti-packed-relative-decode.csv)

The fused attention path eliminates padding and a full-table subtraction on every global layer. On a 2,048-cell cache with 12 query heads and a 1,024-position learned bias, preparing the bias and running attention took 45.40 us for 23 queries, previously 71.80 us. For 2,048 queries it took 2.26 ms, previously 4.66 ms. With identical projected inputs the inline sink reproduced the prior MMA results bit for bit, including positions outside the learned extent. Changing the projection width can still change its own rounding. The largest observed absolute output difference at 2,048 queries with the compact projection was 0.000951. [Relative attention timings and arithmetic controls](data/rtx5070ti-relative-sinks.csv)

Keeping 32 scheduler graphs now enables reuse across compatible slot changes and gives each Inkling session an indexed convolution-state row. For 69 turns rotating across 23 conversations on the Q3 fixture, the default three graphs had zero reuses, retaining 32 under the old implementation produced 46, and the new configuration produced 68. All 11,904 checked log probabilities were identical across these configurations. A branch after token 2,048 of a saved 2,300-token prompt now reuses the full 2,048-token checkpoint. This reduced the prompt work from 304 tokens to 48 with the same greedy result. The optional `--checkpoint-every N` selects the interval.

Separate SWA precision settings were silently ignored on ordinary sliding-window models using the same public flags. A two-layer Gemma 3 fixture previously allocated two F16 K/V caches when its SWA cache was set to Q8_0. The corrected loader allocated F16 for global attention and Q8_0 for sliding-window attention and decoded successfully. It rejected quantized V when Flash Attention was explicitly disabled.

### Session pressure and deep continuation

With 23 occupied slots in a 32,768-token pool, a growing conversation reached 7,769 tokens. The server saved the four oldest idle slots to RAM as it freed their KV cells. The displaced conversation later restored 1,100 of 1,100 tokens and evaluated only the six new ones. On a larger pool the mixed-Q3 fixture served a cold 200,000-token reader while all 22 peers continued streaming, using four logical tensor ranks on one 5070 Ti. The server reported the full 200,000 tokens evaluated and zero reused. These requests used the 262,144-token session cap and the pinned derivative's 128,000 scaling floor.

Nine mixed runs rotated the historical implementation and two early attention candidates through the same workload. The historical median reader time to first token was 10.29 s. The native-sink candidate with 32 graphs and fixed convolution rows had a 9.43 s median and a 16.89 s worst result. Its median pooled peer p95 gap was 79 ms, versus 93 ms historically.

Eight further runs compared the selected inline implementation and the historical binary, reversing the order on alternate pairs. Across four runs per build, the median reader time to first token was 11.37 s historically and 9.31 s on the selected implementation. The median pooled peer p95 gap fell from 103 to 79 ms and median per-peer throughput rose from 18.7 to 22.9 tokens/s. The selected build had a shorter reader time in three of the four pairs. All 22 peers spanned the cold reader in all seventeen runs. Individual timings overlap and all four ranks share one physical GPU here. The real Q3 model and the target interconnect determine deployment performance. [All seventeen mixed runs](data/rtx5070ti-200k-serving.csv)

One 200,000-token synthetic continuation changed its greedy choice between cold prefill and RAM restore. Fresh servers with the identical prefix, token 107 and the same 17-token suffix reproduced this behavior on the historical binary itself. Cold prefill chose 47 and both resident and RAM continuations chose 117. On the historical cold path the two tokens were separated by 0.00090 in log probability. The updated code with the padded attention reference reproduced all 128 historical log probabilities for each path exactly. With the first native-sink implementation, synchronous and asynchronous restoration returned identical distributions with both token 107 and a separate token 42 continuation. Turning indexed graph reuse off also left the token 42 distribution unchanged. The restore path reused the full prefix in each case. Real-model long-context quality remains a separate measurement.

The selected CUDA MMA kernel subtracts the per-query sink before the original FP16 rounding inside attention. On the same 200,000-token continuation, all 128 returned log probabilities again matched the historical binary exactly for each of cold, resident and RAM, and synchronous and asynchronous restore matched each other. To reproduce the old padded arithmetic through the launcher, add `--reference-sinks`. A separate synthetic prompt using the driver's tokenizer-based test restored all 200,000 tokens, and all three paths selected token 117. The maximum difference on shared top-32 entries was 0.071 between RAM and cold and 0.0052 between RAM and resident. This illustrates why both controls are reported.

The final rebuild passed all 54 registered Inkling engine tests, including all eight CPU-reference full-width 384-expert projection cases and the complete MoE block check. The separate KV mask and residual operator checks passed. Compute Sanitizer reported zero errors across 11 residual and clip cases. All 19 launcher tests, five HTTP cache tests and five CPU/CUDA mixed-Q3 server configurations passed. These checks use synthetic weights. Per-rank memory headroom, PCIe collective time, the cost of transferring the global position vector (up to 9 MiB per microbatch at this capacity), real routing skew and quality at 262k remain measurements for the real pack.

### 256k coding input

The Q3 launcher now provides a 294,912-token slot. The exact-fill test used 262,144 input tokens and requested the remaining 32,768 tokens as output. Shorter histories leave more space for generation. Its 23 slots share the 2,359,296-token F16 pool. The pool covers eight maximum-length conversations, with shorter conversations drawing only the cells they use.

On the local mixed-Q3 fixture, four logical tensor ranks on one RTX 5070 Ti evaluated a cold 262,144-token input and generated all 32,768 requested tokens. All 22 peers spanned the prefill. Time to first token was 15.63 s and the pooled peer p95 delivery gap was 90 ms in this run. The resident and RAM-restored continuations reused 262,144 tokens, and the cold control evaluated the full prompt. All three chose the same next token. The largest difference over shared top-32 log probabilities was 0.0042 between RAM and resident and 0.063 between RAM and cold.

A separate five-turn conversation grew from 262,144 to 294,655 input tokens. Every turn returned 128 tokens without truncation. On the last turn the server reused 286,847 tokens and evaluated 7,808. Testing an exact fit also exposed a server reporting bug. The server had marked a fully delivered reply as truncated when its final requested token filled the window. It now flags truncation when capacity prevents further generation. The HTTP regression checks replies below, exactly at and beyond capacity, and an end-of-generation token at the boundary. These results measure serving behavior with synthetic weights. Coding quality at this depth still needs the calibrated abliterated pack. [Local 256k results](data/rtx5070ti-256k-session.json)
