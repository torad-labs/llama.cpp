# GLM-5.3-Flash on two SM120 cards

The goal is at least 200 delivered sampled tokens per second for one active
request on two RTX PRO 6000 Blackwell Server Edition cards, while retaining the
qualified mixed IQ3_XXS/Q8_0 model, full target vocabulary, F32 recurrent state,
sampling behavior and three-slot capacity. This is an experimental bundle.
Compilation and CPU tests do not establish GPU correctness or a speedup.

The comparison and rollback engine is commit
`776b8f577dec45f2fba79b6a41ae8b782f5fc3b3`, archive SHA256
`48358002368846e49d93da500a852f8b6fb51a53655d563fdbdacddb6c8aa4ef`
(`glm53-flash-2026-10-23`). Its recorded rates were 140.60 tok/s at a 1M token
allocation/ubatch 512 and 141.28 tok/s at 512K/ubatch 1024. These are historical
baseline observations; a new comparison must run the same baseline again.

## Complete profiles

Use `--glm53-profile sm120-balanced` before loading the model. `canonical` turns
the new experiments off in the candidate executable; it is not a replacement for
the pinned baseline artifact. Profile changes require a new process and model
reload. Resolution validates dependencies and prints every effective setting.
Individual environment overrides are available for correctness tests; timed
qualification uses a complete profile without overrides.

Boolean overrides accept `0/1`, `false/true`, `off/on`, `no/yes` and integer values, ignoring case and surrounding whitespace. Widths and ring sizes accept their listed numeric choices with surrounding whitespace. Resolution writes normalized values before kernel dispatch. Server argument parsing defers profile application until remote presets are resolved and the process is known to load a model, so a router does not export implicit defaults as overrides for its children.

The sampling row below is the profile default. An explicit `--backend-sampling` remains enabled under `canonical`; its existing CLI choice takes precedence.

| Choice | canonical | sm120-balanced | sm120-wide | sm120-direct |
|---|---:|---:|---:|---:|
| Q8 codes/scales packing | off | on | on | on |
| Q8 TMA / ring slots | off | on / 2 | on / 4 | off |
| IQ3 compact ownership / ring slots | off | on / 8 | on / 4 | on / 8 |
| KDA value columns per warp | 1 | 2 | 4 | 2 |
| Shared KDA q/k/decay front | off | on | on | off |
| Separate current-state allocations | off | on | on | on |
| L2 persistence request | off | on | on | off |
| One-kernel mHC / CTA publication | off | on | on | on |
| Completed collective + mHC post | off | on | on | off |
| Target backend sampling | off | on | on | on |

Packing is a prerequisite for Q8 TMA, the state arena is a prerequisite for its
persisting-cache hint, and CTA publication requires the one-kernel mHC front.
Disabling an implicit prerequisite disables its dependent choice; an explicit
contradiction is rejected. These profiles reject non-F32 recurrent state and the
Q8 warp-count override, which changes the logical reduction.

## Representation and lifetime contracts

Eligible Q8 weights are contiguous 2D SM120 allocations with K divisible by 256.
Codes and unchanged half-scale bits occupy separate aligned regions in each
physical row, with the same total bytes as canonical Q8_0. The backend owns the
layout metadata; tensor types and host set/get/copy bytes remain canonical.
Higher dimensional expert and attention weights remain canonical. Eligibility is
decided before the first upload; a later write cannot silently change the layout.

MMVQ, MMQ, gather, conversion/cuBLAS and copy readers understand the layout.
Unsupported readers are rejected by backend support selection. Views retain the
physical row pitch; a matmul that crosses a packed physical-row boundary falls
back. Every varying row/channel stride must preserve that physical row pitch.
Tensor-parallel shape checks use the logical graph; separate storage checks inspect each rank's allocated sources. Unresolved packed views use canonical fallback, while ordinary Q8 compute-cache views remain schedulable. Nonidentity overlapping copies require scheduler staging. Partial and
pitched uploads reconstruct only bounded pieces. One shared transfer allocation
is capped at 4 MiB per physical card and retained until its last buffer owner is freed; failure uses a bounded host-row overlay. Events order scratch reuse across streams without synchronizing every asynchronous transfer. No complete
duplicate GPU weight copy is retained. Buffer destruction owns descriptors and
layout metadata, and reinitialization removes every overlapping stale allocation entry.
Pitched transfers reuse one scratch allocation for all rows, and packed memset writes directly on the device. Ordinary compute buffers avoid the layout registry; repeated weight lookups cache the buffer generation, row metadata and tensor maps.

TMA uses two stable tensor maps, one for codes and one for scales. The producer
publishes exact transaction counts and alternates full/empty barrier phases in a
2- or 4-slot ring. Its four-row, K=1024 tiles use unswizzled aligned transport.
Unsupported geometry uses direct loads. TMA changes transport and output-row
parallelism while preserving each output's logical K partition and fold. It is
not Tensor Memory (`tcgen05`/TMEM); that feature is not available on this SM120
target.

The compact IQ3 path couples codebook replication, producer ownership, consumer
warps, ring storage and eviction. Reuse of an unpacked tile requires at least
three routed uses; distinct routes keep the per-pair loop. The dedicated F32 KDA
variants retain one independent recurrence and accumulation chain per value
column. Shared q/k/decay publication does not alter beta, decay bounds,
convolution, normalization or prefix snapshot semantics.

Each KDA layer's current state occupies the front of its own allocation, followed
by its existing prefix snapshot planes. Only the current-state interval may be
hinted for persistence. Requested, maximum and granted L2 limits are distinct;
ordinary-cache fallback is valid. Virtual split devices and competing contexts
do not each reserve the same physical set-aside. The last owning context resets
the hint and limit. Prefetch admission subtracts the actual granted reservation.
All three slots and eight prefix snapshots still count toward allocation fit.
The active-state budget counts the layers assigned to each buffer type, so layer splitting does not charge every card for other cards' layers.

The local mHC publication chain uses acquire/release device-scope tickets and a
CTA barrier. Peer reduction still uses the existing system-visible packet
protocol, counter and buffer reuse. The collective epilogue only consumes a
completed reduction with a compatible first mHC consumer in the same captured
graph. Incompatible shapes, graph ownership or copy-engine routes keep the
existing handoff. Meta passes the following graphs explicitly through the optional `comm_allreduce_next` interface; the ordinary weight-prefetch hint never authorizes executing a consumer. Each following graph compute and capture teardown clears consumer markers.

Target sampling uses the full vocabulary and the existing supported-chain
implementation. Grammar and unsupported chains retain their existing fallback.
The draft's 98,304-entry map contains global target token IDs; it does not reduce
the target vocabulary. MTP draft depth remains two, with adaptive threshold 0.18.

## Validation and accounting

New CPU checks cover generated canonical-byte transfers, partial updates, aliases,
canonical reader reference graphs, state-window geometry, allocation reuse, accepted-prefix rollback,
independent slots, profile dependencies, router/environment handling and delivered-token accounting. Device
cases additionally exercise both actual cards, every Q8 direct/TMA/unroll route,
cuBLAS conversion, all IQ3 rings at real/odd dimensions, KDA ownership variants, mHC publication, real peer
inboxes, forced-host and mixed routes, duplicate-device fallback, graph reuse,
target sampling and capacity. An absent GPU or an unsupported case is a gap.

The scripts in `scripts/glm53/` retain raw responses and identities. They do not
rent, download a model, stop a provider instance or publish an artifact. Run them
only on the dedicated test allocation after installing the external stop deadline.
Use the portable test executables linked to the exact candidate libraries.

The primary workload uses a 1,048,576-token allocation, ubatch 512, batch 4096,
three configured slots and one active request. The 524,288/ubatch-1024 companion
is reported separately. Both use tensor split 1:1, Q8 K/V/index caches, temperature
1, top-p 0.95, repeat penalty 1.1 over 256 tokens, seed 530 and ignore-EOS. Four
pinned English/Chinese/code/tools fixtures run three times in each ABBA leg,
384 outputs per request, 24 requests per arm. The rate is
`sum(predicted_n - 1) / sum(predicted_ms / 1000)`. Both opposite-order pairs must
improve and no category may regress more than 2%; the primary aggregate must
reach 200 tok/s. Draft acceptance or a kernel microbenchmark is not this result.

Distribution comparisons at 2,048, 4,096 and 16,384 tokens require
`abs(meanKld) <= 1e-6` and at least 99.99% identical top tokens. Capacity includes
one 32K request, three concurrent 32K requests, a 32K follow-up, and a 131,072-token
prompt plus 64 outputs under the 1M allocation. That last case does not establish
a fully occupied 1M prompt. Instrumented runs never supply the timed rate.

Optional `GGML_CUDA_ROUTE_STATS=1` records expert multiplicities and verification
row counts at backend destruction. Server timings separately record drafted,
accepted and delivered tokens, verification attempts/rows and replay counts.
Use these only in diagnostic legs; normal timing leaves route counters off.

Build and local test example (use the host's normal build gate):

```sh
cmake -S . -B build-sm120 -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=120a -DLLAMA_BUILD_TESTS=ON
cmake --build build-sm120 --parallel 4
python3 -m unittest discover -s scripts/glm53 -p 'test_*.py'
```

GPU checks and speed, portable packaging, independent implementation review,
publication and production activation are separate unfinished outcomes until
their receipts exist for the same candidate artifact and selected profile.
